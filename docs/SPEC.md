## 1. プロジェクト概要

通信キャリア **SNC**（So-net / ソニーネットワークコミュニケーションズ系。以下 SNC）が、光回線等の販売代理店網（**1次代理店 → 2次代理店 → 販売員**）を管理するための BtoB 業務 Web アプリケーション **「Airis」**（別名: AI事務局 / 販売代理店支援ポータル）を新規開発する。

- 開発・運用ベンダーは **サスラボ社**（サステナブル・ラボ株式会社）。
- 利用者は SNC 社内（管理者・運用者・閲覧者・サポート窓口）、サスラボ社（システム管理）、1次/2次代理店の管理者、販売員。
- 従来 Excel とメールで行っていた以下の業務を Web 化する:
  1. アカウント（Airisアカウント・販売員ID・訪販員）の申請・承認・管理
  2. 稼働日報（訪販・テレマ）の提出と集計
  3. 稼働提出物（6種の申請書フォーマット）の提出・承認・提出状況管理
  4. お知らせ・情報周知の配信と既読管理
  5. ホットライン窓口・消費者センター窓口の案件管理（SNC⇔代理店のやりとり）
- AI系機能（AIチャット/AI研修/AIロープレ）とゲーミング要素は**権限表に枠だけ存在し、詳細要件が未確定**。本フェーズでは実装せず、サイドメニューにも出さない（§7.13。権限定義の枠のみ先行）。

### 用語集

| 用語 | 意味 |
|---|---|
| SNC | 通信キャリア側の組織。PS1課/PS2課/PS3課、統括部などが登場する |
| サスラボ社 | 本システムの開発・運用ベンダー |

## 2. 技術スタック（指定）

> 発注者が別のスタックを望む場合はこの節だけ差し替える。以降の仕様はスタック非依存。

- **フレームワーク**: Next.js（App Router）+ TypeScript（strict）。フロント/バックエンド一体。
- **DB**: PostgreSQL 16 + Prisma ORM。開発環境は docker-compose で提供。
- **認証**: 自前実装（Credentials + TOTP）。セッションは **DBバックドのセッションストア**（絶対期限・アイドル期限を制御するため。JWTのみの構成は不可。§10.2）。
- **パスワードハッシュ**: Argon2id（ソルト自動 + アプリケーションペッパーを環境変数で付与）。
- **MFA**: TOTP（RFC 6238, Google Authenticator互換）。`otplib` + QRコード表示。**SMS/Email をMFA要素にしない**（SEC要件②#11）。
- **UI**: Tailwind CSS。コンポーネントは shadcn/ui ベース可。デザイントークンは §11 に従う。
- **ファイルストレージ**: ストレージ抽象化レイヤを実装（開発: ローカルディスク / 本番: S3互換）。DBにはメタデータのみ。
- **メール送信**: 抽象化レイヤ（開発: コンソール出力 / 本番: SMTP or SES）。
- **Slack通知**: Incoming Webhook（URLは環境変数。未設定時は「未設定」表示にして送信スキップ。プロトタイプUIにも「Slack: 未設定」表示がある）。
- **テスト**: Vitest（単体）+ Playwright（E2E）。
- **品質**: ESLint + Prettier + `tsc --noEmit` を CI（GitHub Actions）で必須化。
- **タイムゾーン**: Asia/Tokyo 固定。日付表記は `YYYY-MM-DD`、日時は `YYYY-MM-DD HH:mm`。

## 3. アーキテクチャ共通要件（全機能横断）

以下は**全機能に共通で適用**する。個別機能の実装時に毎回確認すること。

### 3.1 テナント分離・データスコープ
- 全業務テーブルに代理店スコープ（`primaryAgencyId` / `secondaryAgencyId`）を持たせ、**認証セッションから解決したスコープをサーバ側で必ず検証**する。クエリパラメータ等クライアント由来の代理店IDを信用しない。
- スコープ規則:
  - SNC系ロール（①〜⑥）: 全代理店を横断参照可（ただし機能権限表 §5 に従う）
  - 1次代理店（⑦）: 自店 + 配下の2次代理店のデータのみ
  - 2次代理店（⑧）: 自店のデータのみ
  - 販売員（⑨）: 自分のデータのみ（日報など）
  - 稼働終了代理店（⑩）: 当該1次代理店の窓口案件のみ
- PostgreSQL の Row-Level Security も併用する（アプリ層チェックとの多層防御。SEC要件①）。

### 3.2 RBAC
- ロールは §4 の10種を enum で定義。**機能×操作の権限は §5 の表をコードで表現**し（例: `permissions.ts` の宣言的マップ）、API層・UI層の両方で判定する。
- UIでは権限のない操作ボタンを非表示、権限のないページはナビから除外。APIでは 403 を返し監査ログに記録。

### 3.3 監査ログ・アクセスログ
- **監査ログ（audit_logs）**: 誰が（actor: アカウントID）・いつ・何を（action）・何に対して（対象リソース種別+ID）・結果（成功/失敗）を記録。対象イベント: ログイン成否、ログアウト、パスワード変更、MFA登録/リセット、アカウントの申請/承認/却下/変更/停止/削除、権限変更、各業務データの作成/変更/削除/承認、ファイルのアップロード/ダウンロード、CSVエクスポート、設定変更。さらに**機微データの「閲覧」も記録対象**とする: 個人情報を含む詳細取得（販売員・訪販員申請の詳細参照。ブラックリスト欄の表示は必須記録）、窓口案件詳細の参照、SNC系ロール（①〜⑥）によるテナント横断のデータ参照（SEC要件① / ②#35）。**保存期間1年以上**（SEC要件②#35,36）。
- **アクセスログ**: ログイン日時・IPアドレス・User-Agent をアカウント単位で記録。**CSVダウンロード機能**を管理者向けに提供（要件1-6, 2-11, 3-9）。
- 不正利用防止（要件1-9）: 同一アカウントの並行ログイン・普段と異なるIPなどの不審シグナルを検知したら、SNC管理者アカウント宛にアプリ内通知+メールでアラート。

### 3.4 論理削除と保持期間
- アカウント系（Airisアカウント・販売員ID・訪販員申請）は物理削除しない。「削除済」ステータスで**1年間保持**し、1年経過後は**個人情報カラムのみ匿名化して分析用に残す**（要件1-4, 2-3, 3-3）。匿名化は日次バッチで実施。
- 誤削除に備えた**バックアップ/復旧機能**: 削除済みレコードを管理者が一覧・復旧できる（要件1-5, 2-10, 3-8。プロトタイプにも「保持バックアップから復旧」「復旧対象ID一覧（JSON）」ボタンがある）。

### 3.5 ダミー表示モード（SNC閲覧アカウント④専用）
- ④は「Airisがどんなサービスか他部署が見るためのアカウント」。§5 の表で「ダミー表示」となっているページは、**本物そっくりの偽データ（シードで用意した架空データ）を表示**し、実データへは一切アクセスさせない。
- 実装方針: ④のセッションではリポジトリ層をダミーデータソースに差し替える。書き込み操作は全て無効化。**例外**: Airisアカウント申請（④は自ロール④の申請のみ可 §6.1）は実データとして受け付ける。

### 3.6 CSV入出力
- 文字コードは UTF-8（BOM付き）で Excel 互換に。取込は行単位バリデーション→エラー行レポート（何行目・何列・理由）を返し、**全件ロールバック**（部分取込しない）。
- 出力（棚卸CSV・アクセスログCSV・GiGaCC連携CSV等）は監査ログに記録。

### 3.7 通知基盤
- アプリ内通知（ヘッダのベルアイコン）+ メール + Slack の3チャネル。機能ごとに使用チャネルを §7 で指定。通知はテーブルに永続化し、既読管理する。

### 3.8 ファイル管理
- アップロード対象: 承認証跡、提出物、誓約書PDF、周知資料の添付。上限は既定 20MB（環境変数で変更可）。許可拡張子はホワイトリスト方式（xlsx/pdf/png/jpg/zip 等）。ファイル名はサニタイズし、ストレージキーはUUID。ダウンロードは権限チェック付きの署名URL or ストリーミング。

## 4. アカウント体系（10ロール）

| # | ロール名 | 区分 | アカウントID文字列 | 想定利用者 |
|---|---|---|---|---|
| ① | サスラボ社システム管理アカウント | 管理者 | `airis_slb_sys_000` | サスラボ社社員（SNC承認済み） |
| ② | SNC管理者アカウント | 管理者 | `airis_snc_adm_000` | SNC課長以上または権限移譲された担当者 |
| ③ | SNC運用者アカウント | 管理者 | `airis_snc_ops_0000`（連番4桁） | PS2課の代理店担当（エリア営業SV含む）、PS3課のAiris担当 |
| ④ | SNC閲覧アカウント | 一般 | `airis_snc_vew_000` | PS1課・統括部など他部署の確認用（**ダミー表示**） |
| ⑤ | SNCサポート（ホットライン窓口） | 一般 | `airis_snc_spt1_000` | ホットライン窓口担当 |
| ⑥ | SNCサポート（消費者センター窓口） | 一般 | `airis_snc_spt2_000` | 消費者センター窓口担当 |
| ⑦ | 1次代理店管理者アカウント | 管理者 | `airis_1xxxxxx_000`（x=代理店コード） | 1次代理店の管理者 |
| ⑧ | 2次代理店管理者アカウント | 一般 | `airis_2xxxxxx_000` | 2次代理店の管理者 |
| ⑨ | 代理店一般アカウント（販売員ID） | 一般 | `xxxxxxC000`（x=代理店コード） | 営業担当者。販売員IDでそのままAirisにログイン |
| ⑩ | 稼働終了代理店アカウント | 一般 | `airis_1xxxxxx_000` / `airis_2xxxxxx_000`（稼働終了した⑦⑧のIDをそのまま流用。**権限一覧★を正とすることで確定**） | 稼働終了した1次代理店。窓口対応のみに限定 |

- 末尾の `000` は連番（③のみ将来を見越して4桁）。ID文字列は申請承認時にシステムが自動採番する。
- ⑨販売員IDは「氏名・生年月日・電話番号・代理店名」で登録する別系統のアカウントだが、**どちらの系統でも同じログイン画面からAirisにログインできる**こと（要件1-8, 2-5）。

### 4.1 ステータス

- **Airisアカウント（①〜⑧⑩）**: `承認前` → `本登録`、`停止中`、`削除済` の4種（要件1-4）。**enum値と画面表示ラベルの対応**（表示はプロトタイプ準拠）: 承認前=「承認待ち」/ 本登録=「登録済み」/ 停止中=「停止」/ 削除済=「削除済」。統計カード等もこのラベルに統一する（「承認中」等の揺れた表記を新たに作らない）。
- **販売員ID・訪販員申請**: `申請中` → `仮登録` → `本登録`、`停止中`、`削除済` の5種（要件2-3, 3-3。申請中=承認前、仮登録=1次承認済み等の中間状態。GiGaCC連携CSVは**本登録のみ**出力対象）。
  - 訪販員申請の一覧では、申請レコードが無い販売員を「未申請」と表示する（「未申請」はステータス値ではなく表示上の状態）。
  - 申請区分（`稼働` / `抹消`）はステータスとは**別のフィールド**。「抹消」申請が最終承認されると当該訪販員登録を抹消（削除済へ遷移）する。
- 状態遷移はサーバ側で厳密に制御し、遷移イベントを履歴テーブル（例: `requested` / `approve_first` / `final_approve` / `reject` / `suspend` / `resume` / `delete`）に記録。プロトタイプ同様、一覧に履歴を表示する。

### 4.2 認証仕様（§10 と併せて必須）

| 項目 | 管理者アカウント（①②③⑦） | 一般アカウント（④⑤⑥⑧⑨⑩） |
|---|---|---|
| パスワード最小桁数 | **20桁** | **14桁** |
| 有効期間 | 90日 | 180日 |
| 再利用禁止 | 過去24世代 | 過去24世代 |
| 初回ログイン | 初期パスワードからの変更を強制 | 同左 |

- **MFA**: ID/Pass + TOTP（Google Authenticator）。①〜⑧⑩は必須。⑨販売員IDは**機能としては必須実装、利用は任意**（要件2-5。**発注者確認済みで確定** — §14-12）→ ⑨はMFA登録をスキップ可能にする。
- **アカウントロック**: 30分間に10回失敗で30分自動ロック（SEC要件②#12）。
- **セッション**: 絶対期限24時間以内 + アイドル60分以内で失効（SEC要件②#13）。
- MFAリセット・パスワードリセットは管理者代行フローを用意（②③が実行、監査ログ必須）。
- **共有アカウント禁止**: 同一権限を複数名で使う場合も個人ごとに発行（SEC要件①。UIの説明文にも明記する）。

## 6. 申請・承認フロー

「アカウント申請フロー★」シート + フロー図の文言より。

### 6.1 Airisアカウント（①〜⑧⑩）
1. **申請**: 各ロールが申請できる対象は限定される — ①②→①〜⑩すべて / ③→③〜⑩ / ④→④のみ / ⑤→⑤のみ / ⑥→⑥のみ / ⑦→⑦⑧ / ⑧→⑧のみ。
2. 申請時に「氏名」「メールアドレス」を入力し、**上長承認証跡ファイルのアップロード必須**（ファイル選択 / ドラッグ&ドロップ両対応。要件1-3）。
3. **承認**: ⑧の申請は⑦の**1次承認**を経てSNCへ。SNC側の**最終承認は基本③、②でも可**。SNC内部からの申請は②が承認。SNC一般以上のアカウント発行・権限変更・停止・削除は**必ずSNC課長以上（②）の承認**を要する（要件1-1）。
4. **最終承認時にアカウントID（認証ID）を自動採番・発行**し、仮パスワードを承認者に一度だけ表示する。仮パスワード・TOTP秘密鍵は申請データに保存しない（プロトタイプの説明文どおり）。
5. **停止・削除**: Airisアカウントの停止・削除は**①②のみ**（§5.1のとおり）。①は運用ルール上、SNC課長以上の依頼がある場合のみ実施（システム上は可能でよい）。

### 6.2 販売員ID（⑨）
1. 登録情報: **代理店名（主に2次代理店名）・氏（姓/名別枠）・生年月日・電話番号**（メールアドレスは任意）。
2. 申請経路: ⑧が申請→⑦が1次承認→③（または②①）が最終承認。⑦が申請した場合は自ら1次承認可。SNC側（①②③）も申請・承認可能で、**①②③は自ら申請した案件を自己承認（最終承認）することも可能**（販売員ID・訪販員申請共通。発注者確認済み）。
3. **CSV一括申請**対応（初回数百件規模。要件2-6）。CSV必須列: 姓、名、生年月日（YYYY-MM-DD）、電話番号、代理店コード。任意列: メールアドレス。
4. 承認されると販売員ID（`xxxxxxC001` 形式、C+3桁連番）を発行。**本登録**の販売員のみ「GiGaCC連携用CSV出力」の対象。
5. 日報提出のため、販売員IDでAirisにログイン可能（ロール⑨）。
6. **停止・削除フロー**（販売員ID・訪販員申請共通）: **権限一覧★のとおり①②③⑦が停止・削除を実施可能**（⑦は自店配下のみ）。フロー図の「原則②のみで削除」「⑦では削除できない」の注記は、発注者確認により**権限一覧★を正**とすることで解決済み（§14-11。運用ガイドとしてのみ扱い、システムでは制限しない）。

### 6.3 訪販員申請
1. **販売員IDの登録後にのみ申請可能**（逆順不可）。販売員ID取得OKでも訪販員申請NGのケースは正常系。
2. 申請項目は §7.4 の列仕様どおり。
3. 承認フロー・停止削除フローは販売員IDと同じ（⑧申→⑦一承→③承）。
4. **訪販員IDは発行しない**（登録有無のステータスのみ）。

### 6.4 稼働提出物
- ⑧は**1次店へ提出**→⑦が**1次承認**して**SNCへ提出**→③が**最終承認**（エリア営業が承認）。⑦自身の名義分は直接SNCへ提出。1次店からの提出が多い想定。
- **日報には承認アクションは無い**（提出のみ）。

- 集計・実績確認タブ: 期間・代理店・販売員でフィルタし、KPIカード6枚（プロトタイプ準拠のラベル: `日報件数` / `獲得/成果数` / `生産性` / `成約率` / `提出物` / `最終承認済み`）+ 日報レコード一覧（削除は権限保有者のみ）。

### 7.6 稼働提出物
- 提出物6種（テンプレートファイルを画面からDL可能にする。実ファイルは `docs/materials/フォーマット/` にある）:
  1. 【アライアンス申請書】（項目: 申請日 / SNC承認日 / アライアンス元企業名 / 住所 / URL / 業種 / サービス名 / 月の紹介数）

- 運用: **2次店単位で一元管理**。ファイルアップロード方式（Excelを添付）。フォーム化はしない。
- 提出フォーム: 提出物種別 / 年度（**4月〜翌3月を同一年度として対象月から自動計算**） / 対象月 / 1次代理店 / 提出元代理店（⑦は「1次代理店自身」または配下2次店を選択） / ファイル / メモ。

### 7.7 お知らせ・情報周知
- 2種類のチャネル: **全体向け**（①②③⑦⑧⑨に周知）と**1次店向け**（①②③⑦に周知）。登録・送信は①②③のみ（§5.1）。

### 7.8 ホットライン窓口（SNC側: ⑤①②③）
- ホットライン窓口に寄せられるクレーム・トラブル・問い合わせ案件を一元管理（要件9-1）。
- 画面構成（プロトタイプ準拠）: ヘッダ右端に起票ボタン **「新規依頼」**（青塗りプライマリ）→ 説明バナー →**通知チャネル状態バッジ行**（`Airis内通知: 記録済み` / `Slack: 未設定` / `メール: 未設定` 形式。設定状態に応じて表示）→ 検索+ステータスフィルタ → 案件カードリスト。
- **案件（起票はSNC側のみ。代理店からは新規作成不可）**:
  - 起票フォーム: 依頼テンプレ選択（下記3種+フリー入力）、代理店選択（**1次店名・2次店名までのプルダウン。プルダウンはSNC側のみ**）、ISP受付番号、本文、**対応期限（カレンダー選択）**。
  - 件名の自動生成: `テンプレ名称／代理店名称／ISP受付番号`（**【ホットライン】等の接頭辞は付けない**）。
  - テンプレ3種（9-2確定。本文の雛形ごと実装する）:
    1. **音声提出依頼** — 本文雛形: `■依頼理由 ■顧客要望 ■顧客情報（ISP受付番号: / 代理店コード: / 代理店名称:）`
    2. **代理店様から顧客への架電依頼** — 同上
    3. **代理店確認依頼** — 本文雛形: `■依頼理由 ■確認内容 ■顧客情報（同上）`
    4. フリー入力（テンプレなし）
- **スレッド形式**のやりとり（要件9-3）: 案件ごとに窓口⇔代理店のメッセージを時系列で一連表示。投稿はフォームから（チャットではない）。何往復もラリーする前提。
- **代理店側（⑦⑩）の制約**: 返信のみ可 / 新規起票不可 / **ファイル添付不可** / プルダウン利用不可。自店案件のみ閲覧可。
- **既読管理**: 代理店単位で既読を記録（見逃し防止。要件9-2⑤）。
- **ステータス**: `未対応` / `確認中` / `対応中` / `問題発生` / `完了` を案件画面から変更可能（要件9-1・9-2の表記どおり。値はマスタ化して増減できる実装に）。ステータス変更は履歴として記録し案件画面から参照可能にする（要件9-4）。
- **期限バッジ**: 期限との差分から自動表示 — `期限まで◯日`（グレー） / `本日期限`（黄） / `期限超過 ◯日`（赤）。
- **検索**: 案件ID・件名・代理店のキーワード検索 + ステータスフィルタ（要件9-2⑥）。
- **通知**（メール + アプリ内 + Slack。要件9-2）:
  1. 案件起票時 → 対象1次代理店管理者へ通知
  2. 窓口から返信があった時 → 同上（ラリー中の見逃し防止）
  3. **緊急アラートボタン** → エリア営業（SV=③）と1次代理店管理者へ通知（期限切れ等の催促）
  - 期限切れ案件の**自動リマインド**（日次バッチ）: SNC運用者への通知 + 指定メールアドレスへのメール + Slack通知（督促機能）。
- 案件IDは `HLC-` + 連番/タイムスタンプ形式（プロトタイプ: `HLC-1785771172343`）。
- 履歴確認: 登録情報・やりとり・ステータス変更履歴を後から参照可能（要件9-4）。

### 7.9 消費者センター窓口（SNC側: ⑥①②③）

## 10. セキュリティ要件（リリース条件）

「SEC要件①②に準拠することがクラウドレビューのリリース条件」（要件1-11）。アプリ実装に関わる確定事項:

### 10.1 認証・アカウント
- MFAはTOTP（ソフトウェアトークン）。**SMS/EmailはMFA要素として不可**。
- パスワードポリシーは §4.2 のとおりロール別に強制。ポリシー値は設定で変更可能に。
- パスワードは Argon2id + ソルト（+ペッパー）でハッシュ化。平文・可逆暗号保存禁止（OWASP準拠）。
- アカウントロック: 30分10回失敗→30分ロック。認証エンドポイントにレート制限。
- 初回ログイン時、パスワード変更完了まで他機能へ遷移不可。
- 1人1ID（共有アカウント禁止）。サスラボ社の保守アカウントも個人単位で発行し、同じ監査ログ基盤で記録（ベンダー区分属性を持たせる）。
- 管理系画面へのIP許可リスト制御を設定可能にする（環境変数/設定テーブル。設定変更自体も監査ログ対象）。

### 10.2 セッション
- 絶対期限 ≤24時間、アイドル ≤60分。ログアウトでサーバ側セッション破棄。
- Cookie: `Secure` / `HttpOnly` / `SameSite=Lax`。CSRF対策必須。

### 10.3 データ保護
- 通信は TLS1.2以上（TLS1.1以下無効）。HSTS。
- 保存データはサーバサイド暗号化（AES-256）。SHA-1/MD5 は用途を問わず使用禁止（CRYPTREC準拠アルゴリズムのみ）。
- シークレット（DBパスワード・ペッパー・Slack Webhook等）はコードに含めない。`.env` + 本番はシークレットマネージャ。
- 暗号鍵・シークレットは**年1回以上の交換を前提に設計**する（SEC要件②#42）: ペッパーはバージョンID付きで保持し、ログイン成功時に新バージョンで再ハッシュする方式。セッション署名鍵等の交換手順は `docs/OPERATIONS.md` に文書化。
- データ保存先は国内リージョン（東京）前提。
- テナント分離は §3.1（アプリ層+RLSの多層防御）。
- 解約・削除要件: テナント単位のデータ一括削除機能、個人情報削除機能（§3.4の匿名化と整合）。削除実行時は対象件数・データ種別・実行日時・実行者を含む**削除完了レポートを出力**できること（削除証明用。SEC要件②#31。削除操作自体も監査ログ対象）。

### 10.4 監査・監視
- 監査ログ §3.3。保存1年以上。構造化ログ（JSON）で出力し、収集基盤に流せる形式に。
- `audit_logs` は**append-only 設計**とする: アプリケーションから更新・削除するAPI/経路を持たない（管理者権限でも編集不可）。長期保管・WORM化はインフラ側要件（§10.6）。
- 認証失敗急増・特権操作・エクスポート操作のアラート設計（実装はログ出力+通知フックまで。SIEM連携はインフラ側）。

### 10.5 セキュア開発
- OWASP Top10 / IPA「安全なWebサイトの作り方」準拠: 入力検証（zod等）、出力エスケープ、SQLi（ORM経由のみ）、XSS、CSRF、認可チェックのサーバ側徹底、IDOR防止（すべての詳細取得APIでスコープ検証）。
- 依存ライブラリスキャン（`pnpm audit` / Dependabot）と Docker イメージスキャンを CI に組み込む。
- 本番/検証/開発の環境分離。開発環境で本番データを使わない（使う場合はマスキング）。

### 10.6 インフラ側要件（アプリ実装外・README に記載だけする）
- WAF / CDN / DDoS対策 / GuardDuty等の脅威検知、バックアップ日次以上（RPO≤24h）+ 3-2-1ルール、リストア手順とリストア定期テスト・RTO定義、第三者脆弱性診断（初回リリース前のWebアプリ診断は必須級）、パッチSLA（CVSS 9.0+は1〜5日）、サーバ/コンテナのマルウェア対策（イメージ定期スキャン+短命コンテナ運用の代替統制）、CISベンチマーク準拠のハードニングと構成変更管理、KMSによる鍵管理（年1回以上のローテーション）、インシデント初報SLA（重大時は原則1時間以内）と個人情報保護法の法定報告対応。
- これらは `docs/OPERATIONS.md` に前提条件として書き出すこと（実装対象ではない）。

- 代理店系ロール（⑦⑩）には 8・9 の代わりに統合ビュー**「窓口案件」1項目**を表示する（HL+消セン案件を同一画面・色区別で表示 §7.10。要件9-2⑨）。⑩のメニューはダッシュボードと「窓口案件」のみ。
- サイドメニュー名は「各種資料の提出」、そのページヘッダタイトルは「日報・稼働提出物」（プロトタイプ準拠の名残でよい）。
- **ヘッダ**: 左にページアイコン+太字タイトル、右にロールチップ（薄青ピル）+通知ベル（バッジ付き）。
- ページ本体: 薄いブルーグレー背景（#F5F7FB前後）に白カード（角丸12〜16px、薄い枠線、影は控えめ）。

### 11.2 デザイントークン
- プライマリ: 青 `#2563EB` 系（ボタン・アクティブ状態）。背景 `#F5F7FB`、カード白、境界 `#E2E8F0`。
- テキスト: 見出し `#1E293B`、本文 `#334155`、補助 `#64748B`。
- セマンティック: 成功/承認=緑 `#10B981`、警告/承認待ち=黄（薄黄背景+茶文字）、危険/削除/期限超過=赤 `#EF4444`、無効/停止=グレー。
- バッジは「薄い背景+同系の濃い文字」のピル型で統一。
- 情報バナーは薄青 `#DBEAFE` 角丸ボックス。
- フォント: Noto Sans JP。アイコンは lucide-react 等の一貫したSVGセットを使用（プロトタイプは絵文字だが、本実装ではSVGアイコンに置き換えてよい）。

### 11.3 UIパターン
- 一覧画面の定型: 説明バナー → KPI統計カード（横並び4〜6枚: 大きな数値+ラベル） → セクション見出し+プライマリボタン（「＋ ◯◯申請」） → 検索+フィルタ行 → テーブル or カードリスト。
- テーブル: ヘッダ行薄グレー、セル内は複数行の複合表示可（ID+補足、氏名+メタ情報）。状態依存の行内アクションボタン（承認=緑塗り、停止・削除=赤塗り、編集・詳細=白アウトライン）。横に長い場合はコンテナ内横スクロール。**ページネーション（50件/頁）+件数表示を必ず実装**（プロトタイプは全件表示だが改善する）。
- 窓口案件はテーブルでなくカードリスト（件名+メタ2行+右上にステータスバッジ・期限バッジ）。
- 日付は `YYYY-MM-DD`、区切りは ` / ` で統一。

### 11.4 プロトタイプを真似してはいけない点
- 「localStorage fallback対応」: プロトタイプはブラウザ保存に退避していたが、本実装は**必ずサーバ永続化**。
- アップロード上限「260KB」「PDFは220KB以下」: プロトタイプの制約。本実装は既定20MB。
- 一覧の全件表示（95行を1画面）: ページネーションを実装する。
- 「育成フォロー/成長ハイライト/理解度チェック」: AI研修系の未確定機能。実装しない。
- ステータスバッジの縦書き表示（列幅不足の産物）: 横書きで実装。

## 13. テスト観点（最低限）

- **権限**: §5 のマトリクスをそのままテーブル駆動テスト化（ロール×機能×操作で許可/拒否を全数検証）。ページアクセスも同様。
- **スコープ**: ⑦が他の1次店のデータへアクセスできないこと、⑧が親と兄弟店へアクセスできないこと（IDOR）。
- **認証**: パスワードポリシー・履歴・期限切れ・初回変更・ロック・TOTP成功/失敗・セッション期限。
- **承認フロー**: 申請→1次承認→最終承認→ID発行、却下、①②③の自己承認（販売員ID・訪販員申請）。停止・削除は対象エンティティ別に検証する — Airisアカウントの停止・削除は①②のみ / 販売員ID・訪販員申請の停止・削除は①②③⑦（⑦は自店配下のみ。§14-11で確定）。
- **日報**: 上書き提出、月初見込の初回のみ入力、KPI計算（Excelの期待値と突合）、CSV取込のエラー行レポート。
- **提出物**: 年度自動計算（2027-03 → 2026年度）、提出状況の n/6 集計。
- **窓口**: 代理店から起票・添付ができないこと、自店案件のみ見えること、期限バッジ3態、リマインドバッチ。
- **監査ログ**: 主要操作でログが残ること。
